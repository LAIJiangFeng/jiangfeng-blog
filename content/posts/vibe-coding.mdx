生成式工具把编程现场的起点提前了：口头想法到可玩原型，往往只剩几轮对话。但工程真正关心的，从来不是「能不能生成」，而是**能不能负责**——代码能跑，不等于系统可靠。

这里说的 **Vibe Coding**，不只是「用自然语言换代码」的低门槛操作，更接近一种新的组织方式：**高频生成、持续审阅、结构约束和责任承担同时发生**。

## 问题不是能生成，而是能负责

AI 很擅长局部可用的实现：函数、页面、接口、测试样板都能很快拼出来。系统最难的部分通常不在局部，而在**整体一致性**。Brooks 讲的概念完整性今天仍然准确：目标、术语、边界和约束能否在多轮迭代里保持一致。

贪吃蛇是个好例子。十分钟做出可玩版本不难；再往下测，难度曲线异常、输入穿透、界面事件污染核心逻辑……这些问题不是语法错误，而是**行为边界从未被定义清楚**。模型会补片段，但不会主动替你把系统要求钉死。

开发者角色因此更偏三件事：**定义规则、审阅结果、维护边界**。稳妥工作流往往是：先写清输入输出与失败语义 → 让模型生成候选 → 用测试与评审决定什么进主干。关键不是让模型多写一点，而是让系统在每一轮生成之后仍**可判断、可解释、可拒绝**。

## 效率之外：更快如何变成更糟

「更快」不自动等于「更好」。很多时候，更快只是在更短时间里暴露问题，也在更短时间里**固化坏结构**。

生成式 AI 是放大机制：它能放大正确路径，也能放大错误路径，两边速度一样快。一次草率的依赖、一次未经论证的抽象、一段职责混杂但暂时能跑的实现，经过几轮生成就会变成默认模式，再沉积成代码库的结构倾向。

真正值得追求的效率，是单位时间里**增加确定性、减少未来返工、保留可演化空间**。开发者只要还能对模型输出说「不」，并把否决权用在概念完整性与复杂度控制上，AI 才从产出机器变成能力放大器。

「先这样吧，后面再改」在多数项目里不会自动发生。不良结构一旦进入主干，就会吸附新依赖，变成很难逆转的既定事实。

## 什么叫适合 Vibe 场景的「优雅代码」

优雅首先不是审美，而是**生存策略**：控制维护成本，降低认知负担，延缓熵增，让局部变化尽量局部闭合。

几条彼此勾连的结构约束：

1. **原子化**：状态推进、渲染、输入、持久化分清职责，避免上帝对象。
2. **接口先于实现**：先定接收什么、返回什么、何时失败，再让模型写实现。
3. **文本基础设施**：需求草稿、契约、变更原因可读、可审、可版本化——别把关键约束只留在一次性对话里。
4. **机制与策略分离**：机制保持中立可复用；权限、审批、频控等策略放到配置或策略层。

初稿可以粗糙。真正关键的是始终把初稿当**候选稿**，持续审阅、删减、拆分和重写。

## 始于乐趣，成于责任

兴趣驱动值得认真对待：它带来高密度提问、频繁试错和内在持续性。生成式工具又把从想法到原型的成本压得很低。

但兴趣不足以自动构成工程终点。只要被他人复用、被团队接管、被流程依赖，甚至只被未来的自己反复调用，项目就已进入公共属性——稳定性、可解释性、兼容性与迁移成本随之成立。

**负责任的 Vibe** 不是要求一上来就全量治理，而是识别阶段并调节强度：实验区容许粗糙与高频试错；主干必须有结构约束与质量底线。草稿可以粗糙，草稿不能伪装成成品。

## 复杂性预算

代码生成边际成本下降了，理解、修改、测试与协作的成本结构没有消失。**复杂性预算**回答的是：项目在某一阶段究竟能承受多少结构复杂度。

进入主干前的最低门槛可以很朴素：

1. **可读性**：能否短时间说清意图、输入输出与关键路径。
2. **职责边界**：是否对应一个主要任务，跨层堆叠优先拆。
3. **重复控制**：同一规则多处拷贝视为预算泄漏。
4. **架构服从**：新代码在既有结构里要有明确位置。

超预算信号也该显式：改动跨过多文件却找不到主修改点；新功能必须先修一堆历史例外；一次改动反复引入非预期回归。流程上把 AI 输出当候选稿，超预算直接拒绝，合并前完成必要重构。

## 提问即设计

Prompt 已经是工程产出的上游。提问方式决定搜索空间，搜索空间决定候选结构质量，再决定维护成本。

一套够用的六段式骨架：

1. **Context** — 环境、任务类型、角色与阶段  
2. **Goal** — 可判断的输出目标  
3. **Constraints** — 禁止项与硬约束  
4. **Interface & Data** — 输入输出、异常语义、样例  
5. **Process** — 固定产出顺序，避免一次倾倒  
6. **Review** — 验收与拒绝条件前移  

「帮我写个订单提交接口」和「分层架构、service 创建订单、controller 统一响应、禁止 controller 写业务、失败返回可追踪错误码……」都能得到可运行代码；后者更容易得到**可合并代码**。需求含糊时，最好的第一步往往是：先别写代码，先提澄清问题。

## 评审优先与协作公约

代码产量不再稀缺时，**审查能力**才是核心生产力。评审至少覆盖：正确性、可读性、可维护性、可演进性。把每次 AI 输出当待合并 PR：需求对齐 → 结构先行 → 证据驱动 → 问题分级 → 复审合并。

团队协作上再加几条最低公约：

- **文本化与协议驱动**：影响核心逻辑的 Prompt 入库可审。  
- **先定接口，再做实现**：AI 在既定边界内写局部。  
- **最小上下文**：只给任务真正需要的契约与测试。  
- **最小复现调试**：输入 / 期望 / 实际 / 片段 / 断言模板化。  
- **评审权威**：破坏主线就退回，角色（提交者 / Reviewer / 模块负责人）分清。

## 收放之道

探索区强调速度与学习；生产区强调一致性与责任链路。可执行的切换阈值——满足任意一条就切回工程模式：

1. 代码预计存活超过一周且会持续修改  
2. 将进入主干或跨团队复用  
3. 触及资金、权限、核心算法或用户数据  
4. 涉及异常、并发时序或复杂状态转换  

真正的 Vibe Coder，能力不在永远高速生成，而在**知道何时放开、何时收紧**。把 AI 当高效草稿引擎，把工程纪律当最终发布标准——这两件事同时成立，Vibe Coding 才成为长期有效的方法，而不只是令人兴奋的演示。
