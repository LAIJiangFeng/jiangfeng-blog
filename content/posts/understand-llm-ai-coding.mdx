用好 AI Coding，前提不是背一堆提示词模板，而是先搞清楚：**大模型本质上在做什么**，以及**哪些问题不能靠「换更聪明的模型」解决**。

## AI 是怎么学会「思考」的（极简时间线）

早期是**专家系统**：把人类知识写成海量 `if-else`。世界太复杂、规则难穷尽，也难随变化更新。

接着是**机器学习**：给数据与答案，让机器自己学规律——有监督学习、无监督学习、强化学习各管一类问题。深度学习加深网络层数，特征提取逐渐自动化，但这一阶段 AI 仍更擅长「选择题 / 判断题」。

真正的跃迁来自 2017 年 Google 的 *Attention Is All You Need*：**Transformer** 与**注意力机制**让模型同时看到序列中的词并建模关系，且天然适合并行训练。数据、参数与算力上去之后，基础模型出现**涌现能力**——推理、写代码、组织长文——边界从「选择题」推进到「填空题」和「作文题」。

## 底层特性：预测下一个词

大模型训练目标出奇朴素：给定前文，**预测下一个最可能的 token**。

自注意力大致三步：把词变成向量 → 计算词与词的关联权重 → 加权汇总后再预测。它擅长**统计相关性**，并不天然具备严格的因果理解。「看起来很懂」不等于「真的在按因果推理」。

### 上下文窗口不是无限硬盘

自注意力复杂度约为 \(O(n^2)\)。token 变多，计算与显存近似平方级上涨——这是硬件与数学边界，不是产品经理不想给你更大窗口。

更重要的是：**窗口变大 ≠ 模型能稳定用好全部内容**。长上下文常见副作用：

1. **注意力稀释**：旧规则还在窗口里，权重却被新内容冲淡。  
2. **近因偏好**：离当前生成更近的内容更容易占优。  
3. **中间失落**：开头与结尾相对更受关注，中间大段「看似放进去了，实际利用率不高」。  
4. **信噪比下降**：无关与重复信息越多，越难维持推理一致性。

所以工程上要做的是**上下文工程**：少而准，而不是「能塞尽塞」。

## Harness：模型之外的操作系统

可以把 Agent 系统想成一台电脑：

| 角色 | 类比 |
| --- | --- |
| 模型 | CPU，提供原始智能 |
| 上下文窗口 | 内存，关机就没了 |
| Agent 应用 | 跑在上面的程序 |
| **Harness** | **操作系统** |

没有操作系统，CPU 再猛也只是芯片。没有 Harness，模型再聪明也更像聊天框：长任务中间忘上下文、写出垃圾代码无人门禁、犯了错自己不知道——这些问题**换更大模型也解决不了**。

Harness 核心通常三件事：

1. **规则约束**：架构边界、代码规范、权限、CI / Linter——写进文档还不够，要工具化、可自动执行。  
2. **执行闭环**：拆任务 → 注入上下文 → 调工具 → 测试 → 审阅 → 修正 → PR，人类在关键点介入。  
3. **记忆治理**：每次踩坑沉淀为规则、测试、清单，同类问题越来越少。

**Harness Engineering** 不是改造模型本身，而是在模型外搭一套可运行、可约束、可反馈、可沉淀的环境。

## Claude Code：循环，而不是「答一题」

Claude Code 的核心更接近代理循环：

```text
收集上下文 → 采取行动 → 验证结果 → [完成 or 回到收集]
```

外围挂着 `CLAUDE.md`、Hooks / 权限 / 沙箱、Skills、Tools / MCP、Memory。

### 上下文账本

标称 200K 并不等于 200K 都给你写业务。固定开销往往包括系统指令、Skill 描述符、MCP 工具定义、LSP 状态等；半固定有项目说明与 Memory；真正留给对话、文件与工具结果的动态空间会被吃掉一大截。

一个典型 GitHub 类 MCP 可能带 20–30 个工具定义，合计数千 token；挂多个 Server 时，**固定开销轻松到数万 token**。装插件前先算账。

### Plan Mode

价值在于**探索与执行拆开**：探索阶段以只读为主，澄清目标与边界、确认方案后再动文件。执行成本应发生在计划确认之后。

### Subagents：隔离比并行更重要

Subagent 是独立实例、独立上下文、限定工具，干完回摘要。最大价值常常不是「并行」，而是**别把扫库 / 测 / 审的海量输出灌进主线程**。

配置时显式约束：`tools` / `disallowedTools`、任务用 Haiku/Sonnet、关键审查用更强模型、`maxTurns` 防跑飞、需要改文件时用 worktree 隔离。避免子代理权限与主线程一样宽、输出格式不定、强依赖共享中间状态却硬拆成多个 subagent。

### Skills：按需加载的工作流，不是模板坟场

好 Skill 的描述应回答「**何时该用我**」，而不是长篇自我介绍。正文放边界与步骤骨架，大资料拆到 supporting files；有副作用的 Skill 设 `disable-model-invocation: true`。

渐进披露：先索引与骨架，再按需取细节。描述符常驻上下文——写短一点：

```yaml
# 低效（几十 token 废话）
description: |
  这个 skill 用于帮助你审查 Rust 项目的代码变更……

# 高效
description: 用于 PR 审查，重点关注正确性。
```

经验法则：高频 → 可自动触发但描述极短；低频 → 禁用自动调用、手动触发；极低频 → 别做成 Skill，改成 md 需要时 `@`。

### Hooks：确定性逻辑别交给临场发挥

格式化、保护文件、Session Start 注入分支与环境、任务完成通知——适合 Hooks。需要大量语义判断、长流程、多步权衡的决策，放 Skill 或 Subagent。

### 压缩与会话策略

默认压缩会优先丢掉「可重新读取」的工具输出与文件内容，有时连**关键决策与约束理由**一起冲掉。实用策略：

- 方向错了优先 **rewind**，别在错误树上无限纠错  
- 上下文将满时主动 **/compact** 并写明要保留的方向  
- 大段探索交给 **Subagent**，主线程只收结果  

## 落到日常的几条原则

1. **当统计生成器，不当真理机器**——用测试、类型与评审补因果与责任。  
2. **上下文是稀缺资源**——少挂 MCP、短写 Skill 描述、任务只喂必要文件。  
3. **用 Harness 补模型短板**——规则、闭环、记忆，比「再换一个模型」更稳。  
4. **探索与执行分开**——Plan / 草稿区可以疯，主干必须门禁。  
5. **踩坑写回约束**——同一次错不要交第二次学费。

理解大模型，是为了把期待放在正确位置；用好 AI Coding，是为了在正确位置上搭工程。模型会换，**对业务与边界的深度理解**不会被轻易替代。
